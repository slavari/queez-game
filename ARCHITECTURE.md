# Architecture

## 1. Принципы

Game Pick проектируется как статическое browser-first SPA. GitHub Pages раздаёт неизменяемые
HTML/CSS/JS-файлы, браузер хоста в будущем владеет каноническим состоянием комнаты, а участники
обмениваются командами и снимками по P2P. Постоянного application server и базы данных нет.

Основные правила: feature-based границы, строгие типы на входах, однонаправленный поток команд к
хосту, разделение UI/домена/транспорта и агрегированные публичные результаты без персональных
голосов.

## 2. Текущая структура frontend

```text
src/
├── app/                 # composition root, router, global styles
├── pages/
│   └── home/            # стартовая страница и её тест
└── test/                # общая настройка Vitest
```

Директории несуществующих функций намеренно не созданы. Когда появляется рабочий вертикальный
срез, добавляется `src/features/<feature>/` с минимально нужными частями, например `ui`, `model`,
`lib` или `api`. Общие, действительно переиспользуемые примитивы переходят в `src/shared/`; общая
композиция остаётся в `src/app/`, а route-level экраны — в `src/pages/`.

Планируемые feature-границы:

- room management — создание, вход, полномочия и переходы этапов;
- participants — профиль участника, роль и presence;
- steam integration — разбор разрешённых Steam URL и адаптер внешних данных;
- game catalog — просмотр доступных игр;
- game proposals — личные предложения и связь participant ↔ game;
- game normalization — source adapters и стабильные identity keys;
- voting — приватная отправка выбора и прогресс раунда;
- results — заменяемая rating policy и публичные агрегаты;
- p2p communication — соединения, протокол сообщений и синхронизация.

Feature не импортирует внутренности другой feature напрямую. Общий доменный контракт должен
иметь явного владельца; транспортные DTO и UI view models не подменяют доменные структуры.

## 3. Концептуальная модель

`Room` агрегирует `Participant`, `GameProposal` и опциональный `VotingSession`. `GameProposal`
связывает участника с `Game`, поэтому объединение карточек не уничтожает авторство предложения.
`VotingSession` фиксирует набор игр для раунда и принимает приватные `Vote`. В публичное состояние
попадает только прогресс и `VotingResult`; персональные соответствия voter → choice не
рассылаются.

Типы будут введены тогда, когда появится использующий их сценарий. Это защищает кодовую базу от
пустых интерфейсов, stores и сервисов, которые закрепляют ещё не утверждённые решения.

## 4. P2P и роль хоста

Предлагаемая топология — звезда:

```text
participant ─┐
participant ─┼── WebRTC DataChannel ── host browser (canonical state)
participant ─┘
```

1. Хост создаёт Peer ID/room ID через signaling.
2. Участник соединяется с хостом и отправляет версионированный handshake.
3. Хост выдаёт актуальный snapshot и порядковый номер версии.
4. Клиент отправляет команды намерения, а не произвольные патчи состояния.
5. Хост валидирует роль, этап и payload, применяет команду и рассылает новый snapshot или
   упорядоченное событие.
6. После разрыва клиент повторно подключается и запрашивает snapshot, если версия разошлась.

До реализации необходимо определить runtime-схемы сообщений, versioning протокола,
идемпотентность команд, размер snapshot, heartbeat и backpressure. Любые данные от peers считаются
недоверенными.

Возможное локальное восстановление хоста использует versioned storage adapter поверх
`localStorage`. В memory-state (в будущем Zustand) не должен знать о формате хранения напрямую.
Сохранение не является межустройственной базой и не обеспечивает доступность при выключенном
хосте.

## 5. Анонимность голосования

В первой версии анонимность — свойство интерфейса и публичной модели. Клиенты не получают
чужие `Vote`, а до закрытия сессии получают только общий счётчик завершивших. Хосту для защиты от
повторного голоса всё равно нужно связать соединение/participant ID с фактом отправки, поэтому он
технически способен наблюдать источник сообщения. Это нельзя описывать как криптографическую
анонимность.

Rating policy получает только агрегаты (`proposerCount`, `voterCount`, `participantCount`) и не
зависит от транспорта или UI. Конкретная policy будет добавлена после утверждения формулы.

## 6. Steam и метаданные игр

Будущий frontend отвечает за:

- синтаксическую проверку URL и выбор source adapter;
- отображение loading/error/private states;
- нормализацию ответа посредника в доменную игру;
- локальную дедупликацию по стабильному source/external ID.

Прямой browser fetch возможен только если источник разрешает CORS и предоставляет стабильный
публичный контракт. Steam Community XML может оказаться неполным, закрытым настройками приватности
или измениться без гарантий. HTML scraping не должен проникать в доменную логику.

## 7. Возможный Cloudflare Worker

Worker нужен только там, где браузеру мешает CORS или требуется безопасно спрятать допустимый
серверный credential. Он может проксировать заранее разрешённые Steam endpoints, извлекать
ограниченные публичные поля и возвращать нормализованный JSON.

Worker не хранит профили, комнаты и голоса, не координирует P2P и не принимает произвольный URL.
Обязательны allowlist host/path, строгая проверка ID, таймаут, лимиты размера ответа, допустимые
content types, rate limiting, нейтральные ошибки и cache policy без персональных данных. Worker не
создаётся до подтверждения, что прямого надёжного источника недостаточно.

## 8. Что работает только в браузере, а что требует посредника

| Возможность                                        | Только браузер |                      Возможный посредник |
| -------------------------------------------------- | -------------: | ---------------------------------------: |
| UI, маршруты, локальное состояние, рейтинг         |             Да |                                      Нет |
| P2P DataChannel после соединения                   |             Да |                                      Нет |
| Обнаружение peers / SDP signaling                  |            Нет |              PeerJS signaling или аналог |
| Соединение через сложный NAT                       |      Не всегда |                               TURN relay |
| Чтение внешнего API с разрешённым CORS             |             Да |                                      Нет |
| Steam/metadata при CORS или server-only credential |            Нет |                         Stateless Worker |
| Долговременная доступность комнаты без хоста       |            Нет | Потребовал бы сервер, вне текущей модели |

## 9. GitHub Pages

Vite `base` читается из `VITE_BASE_PATH` и нормализуется. Workflow подставляет имя репозитория,
не предполагая его заранее. TanStack Router использует hash-history, поэтому GitHub Pages всегда
отдаёт корневой `index.html`, а маршрут остаётся после `#`. Сайт не требует Node.js runtime.

Ограничения: нет SSR, HTTP endpoints, WebSocket server, secret storage, rewrite rules или
динамических response headers. Security headers, custom domain и Pages source настраиваются на
стороне GitHub/домена.

## 10. Зависимости и риски

- публичный signaling может иметь лимиты, простой или изменяемую политику;
- WebRTC не гарантирует прямой канал без TURN;
- уход хоста останавливает комнату до появления согласованного восстановления/миграции;
- Steam и сторонние страницы не являются стабильными API и зависят от privacy/CORS/rate limits;
- P2P-клиенты недоверенны: хост обязан валидировать команды и не раскрывать скрытое состояние;
- `localStorage` ограничен объёмом и не подходит для секретов или надёжной персистентности;
- изменение протокола требует явной версии и стратегии совместимости.
